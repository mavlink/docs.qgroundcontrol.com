QGroundControl Release/Branching process ​

Semantic Versioning ​

QGC uses semantic versioning for the version numbers associated with its releases. Semantic versioning is a 3-component number in the format of vX.Y.Z, where:

  • X is the major version.
  • Y is the minor version.
  • Z is the patch version.

Stable Builds ​

The current stable build is the highest quality build available for QGC. Patch releases of the stable build are regularly made to fix important issues.

Stable builds are built from a separate branch that is named with the format: Stable_VX.Y (note, there is no patch number!) The branch has one or more git tags for each patch release (with the format vX.Y.Z), indicating the point in the repo source code that the associated patch release was created from.

Patch Releases ​

A patch release contains fixes to the stable release that are important enough to require an update, and are safe enough that the stable release continues to maintain high quality.

Patch releases increment the patch version number only.

Patch - Development Stage ​

Approved fixes to the stable release are committed to the current stable branch. These fixes continue to queue up in the stable branch until a patch release is made (see next step).

Commits/changes to the stable branch must also be brought over to the master branch (either through cherry pick or separate pulls).

Patch - Release Stage ​

At the point where the decision is made to do a patch release, a new tag with the patch release number is added to the stable branch, indicating the associated source code. Pushing the tag builds and publishes the release binaries; follow the Release Checklist.

INFO

New branches are not created for patch releases - only for major and minor releases.

Daily Builds ​

Development Stage ​

Daily builds are built from the master branch, and this is where all new major feature development happens. The state of master represents either the next minor point release, or a new major version release (depending on the level of change).

A daily build is published only for a master commit whose packages every platform built, so it can trail the tip of master. Each file comes from a build job that passed. Another job of that commit, such as a test, may have failed: the release notes of the daily build then name the workflow whose run didn't pass. No version tag is associated with a daily build. The daily tag belongs to CI, which moves it to the commit that the rolling QGroundControl Daily Build release on GitHub holds. The release notes name that commit, and say so if GitHub didn't let CI move the tag. Because the tag moves, git fetch --tags reports it as rejected in a clone that already has it; git fetch --tags --force takes the new one.

Release Stage ​

When the decision is made to release a new major/minor version the master branch tends to go through an initial lockdown mode. This is where only important fixes for the release are accepted as pull requests.

INFO

During the lockdown phase, new features are not allowed in master.

Once the level of fixes associated with the release slows down to a low level, a new stable branch is created (at this point the master branch can move forward again as the latest and greatest).

Fixes continue in the stable branch until it is deemed ready to release (ideally after a short time)! At that point the new stable branch is tagged with the new version tag and the first stable release is made, following the Release Checklist.

Custom Builds ​

A proposed strategy for branching on custom builds is described in Custom Build Branching.

Release Checklist ​

A release is made by pushing a vX.Y.Z tag for a commit on a Stable_VX.Y branch. The tag push is the release: it starts every platform workflow. Each job publishes its store upload or builder image as soon as it finishes. The downloads are published together, by the Publish Builds workflow, once the Linux, Windows, MacOS, and Android workflows have all passed. A release is stricter in this than a branch build: master and Stable* builds are also published when a workflow failed in a job that builds no package. No step asks for confirmation, and CI can't undo a release. Work through the steps in order.

WARNING

A tag push runs the workflow files of the tagged commit, not those on master. This page describes the workflows on master. Before tagging an older Stable branch, read that branch's .github/workflows to see what its tag publishes.

Publish Builds is the exception: it always runs from master, and it publishes only builds whose workflows mark their packages for it. A Stable branch that doesn't carry these workflow files yet keeps its old behavior, and Publish Builds publishes nothing for it. That is Stable_V5.0 and Stable_V5.1: each of their build jobs uploads its own file to the download server as soon as it finishes, to builds/vX.Y.Z/ and to latest/ whatever the version, and a failed job leaves a partial release. They write no published.json, and their GitHub Release gets no files. Stable_V5.0 uploads with the static AWS keys (AWS_ACCESS_KEY_ID and AWS_SECRET_ACCESS_KEY), which the repository didn't have when this was written, so check that they exist before you expect its tag to reach the download server. After every release from such a branch, latest/published.json names another release than the files in latest/, and latest/ can keep the .sha256 files of that earlier release beside the new packages. Each time, have the record written again for the new tag, with the command under Pre-flight, and have those .sha256 files deleted. Attach the release files to the draft GitHub Release by hand before you publish it (If a job fails midway).

1. Pre-flight ​

  1. Branch. A patch release is tagged on the existing Stable_VX.Y branch. For a new major or minor version:

    1. Create a branch from master named Stable_VX.Y, where X is the major version number and Y is the minor version number.
    2. Create an annotated tag named vX.Y.0-dev on a master commit after the branch point, where the minor version is one greater than the new Stable. For example, after creating Stable 5.1 the tag is v5.2.0-dev: git tag -a v5.2.0-dev -m "QGroundControl v5.2 daily version base". git describe uses this tag to derive daily-build version numbers (About dialog, Android versionCode, Deb/RPM release fields). The -dev suffix keeps it outside the vX.Y.Z pattern that starts release builds. A tag push runs the workflows from the tagged commit, so the commit must already contain the vX.Y.Z release-tag filters; never place the tag on an older commit whose workflows still trigger on v*.
    3. On the new branch, change the links in Download and Install from builds/master/ to latest/. On master, point the stable-docs links in that page and in the user guide introduction at the new branch, and start the next What's New.

  2. Version. No file holds the version number. Builds take it from the nearest tag with git describe, so the tag you push is the version of the release. Choose the next vX.Y.Z and check that it's unused: git ls-remote --tags upstream vX.Y.Z must print nothing.

  3. Commit. Fetch the branch and note the commit you are going to tag: git fetch upstream && git rev-parse upstream/Stable_VX.Y.

  4. Green builds. The Linux, Windows, MacOS, Android, iOS, and Docker workflows must have passed for the branch push of that commit:

    sh
    gh run list --repo mavlink/qgroundcontrol --commit <commit>

    <commit> is the full hash from the previous step.

    Nothing checks this for you. The tag run builds everything again. If a platform fails there, no download is published until its run passes, but the store uploads and builder images of the jobs that succeeded are already out.

  5. Publish Builds. The workflow must be enabled, because someone who stopped it may not have started it again:

    sh
    gh workflow list --repo mavlink/qgroundcontrol --all | grep 'Publish Builds'

    The line must read active. No repository variable switches publishing on or off: an enabled workflow publishes. A disabled one publishes no download for the tag and doesn't make up for the builds that completed meanwhile. After gh workflow enable publish.yml --repo mavlink/qgroundcontrol, start the publish by hand (If a job fails midway).

  6. Download server record. latest/published.json must name the release that latest/ holds:

    sh
    curl -fsS https://qgroundcontrol.s3.us-west-2.amazonaws.com/latest/published.json

    The files that were uploaded before Publish Builds existed have no such record. Without it, Publish Builds can't tell whether the release in latest/ is older than yours, so its S3 latest/ job stops with an error instead of replacing it. If the command fails, or names another release than the one latest/ holds, ask someone with access to the S3 bucket to write the record, as described under Seeding the latest/ record in .github/ci-notes/platforms.md:

    sh
    python3 tools/ci/publish/aws_upload.py seed --tag vX.Y.Z --commit "$(git rev-list -n 1 vX.Y.Z)" > published.json
aws s3 cp published.json s3://qgroundcontrol/latest/published.json --acl public-read

    Here vX.Y.Z is the release that latest/ holds now, not the one you are about to tag. On 2026-11-12 that was v5.1.5, which was published on 2026-10-01, and latest/ had no record. The record to write is therefore that of v5.1.5, unless a newer release has been published since. To check, compare the version in latest/QGC.version.txt (curl -fsS https://qgroundcontrol.s3.us-west-2.amazonaws.com/latest/QGC.version.txt) with the newest published release (gh release view --repo mavlink/qgroundcontrol --json tagName,publishedAt). The record is needed when Publish Builds reaches master, and again after every release from Stable_V5.0 or Stable_V5.1, whose build jobs replace the files in latest/ without writing a record.

  7. Stores. Whether the tag reaches the Play Store and TestFlight depends only on which repository secrets and variables exist (see What the tag publishes). No per-release switch exists, so decide before tagging. Only the push of the tag uploads to them; a workflow that someone starts by hand for the tag doesn't.

  8. Release notes. Preview the generated notes with just release-notes vX.Y.Z, and bring What's New on the Stable branch up to date (see Release Notes).

2. Tag ​

Only the exact tag form matters:

TagCommitWhat happens
vX.Y.Z (three numbers and nothing else)On a Stable* branchA full release: everything in What the tag publishes
vX.Y.ZOn no Stable* branchThe platform workflows skip every build, and Release and Dev Container fail (see below)
vX.Y.0-devOn masterNo workflow runs; the tag only sets the version numbers of daily builds
Any other name, such as v5.2.0-rc1AnywhereNo workflow runs, so nothing is built or published

A vX.Y.Z tag that is on no Stable* branch publishes nothing: no downloads, store builds, builder images, Dev Container image, or release draft. The Release and Dev Container workflows stop with an error that names the tag before they draft a release or build an image.

For a Stable branch that Publish Builds publishes, the stable downloads in latest/ only move to a higher version. A patch release on an older such line, for example v5.2.3 after v5.3.0, is a full release in every other respect, but its downloads go to builds/v5.2.3/ only and latest/ keeps v5.3.0. The summary of its Publish Builds run says holds the newer release v5.3.0 for latest. Stable_V5.0 and Stable_V5.1 aren't such branches: a tag on either replaces the files in latest/ from its own build jobs, even when latest/ holds a newer release.

WARNING

Anyone who can push to the repository can make a release. A vX.Y.Z tag on any Stable* branch is one, including a branch that was only just created, and CI builds it with that branch's workflow files. No file in the repository limits who pushes such a branch or tag. Only repository rulesets that restrict who creates Stable* branches and v* tags do. The repository has none today: its tag ruleset only prevents deleting a tag and moving it backwards. An approval step for the S3 latest/ job of Publish Builds isn't enabled either. It would need a change to publish.yml and to the AWS role, and it would hold back latest/ only: not builds/vX.Y.Z/, the stores, or the builder images (see Publish Builds in .github/ci-notes/platforms.md).

WARNING

No release-candidate tag exists. A candidate can only be built by pushing a plain vX.Y.Z tag, and that is a full release: it replaces the stable downloads in latest/ and, when the stores are configured, goes to the Play Store production track and to TestFlight. The v5.1 release candidates were published this way, as v5.1.0 and v5.1.2.

Create an annotated tag on the commit from the pre-flight and push it:

sh
git tag -a vX.Y.Z -m "QGroundControl vX.Y.Z" <commit>
git push upstream vX.Y.Z

WARNING

Never move or re-push a tag after pushing it. Every push of a vX.Y.Z tag is another release run, which publishes again when the first one has finished. A tag that was moved to another commit replaces the release in builds/vX.Y.Z/, in latest/, and on the draft GitHub Release with the builds of that commit.

What the tag publishes ​

WorkflowA release tag publishes
LinuxQGroundControl-x86_64.AppImage and QGroundControl-aarch64.AppImage, through Publish Builds
WindowsQGroundControl-installer-AMD64.exe and QGroundControl-installer-ARM64.exe, through Publish Builds; they aren't code-signed
MacOSQGroundControl.dmg, signed with the Developer ID certificate and notarized, through Publish Builds
AndroidQGroundControl.apk, signed with the release keystore, through Publish Builds; the tag's push also uploads it to the Play Store
Publish BuildsThose six files to the download server, and with a .zsync file per AppImage to the draft GitHub Release, once all four passed
iOSAn App Store-signed build, which the tag's push uploads to TestFlight; the IPA is kept only as a workflow artifact
DockerThe builder images to Docker Hub as dronecode/qgroundcontrol:<variant> and dronecode/qgroundcontrol:<variant>-<short commit>
Dev Containerghcr.io/mavlink/qgc-dev:vX.Y.Z
ReleaseA draft GitHub Release for the tag with generated notes; Publish Builds adds the files

The download server is the qgroundcontrol S3 bucket behind https://d176tv9ibo4jno.cloudfront.net/. Publish Builds checks every file against its .sha256 checksum and its build provenance attestation. It then uploads all six files, each with its checksum beside it, to builds/vX.Y.Z/, and after that to latest/, and invalidates the CloudFront cache for each directory with one request. It skips latest/ when that holds a newer release, and its S3 latest/ job fails when latest/ has no published.json to compare the release with. It also writes a published.json into both directories, which names the tag and the commit that the directory holds and lists the files of the release and the workflow runs that built them. It attaches the same files and checksums to the draft GitHub Release that the Release workflow created for the tag, together with QGroundControl-x86_64.AppImage.zsync and QGroundControl-aarch64.AppImage.zsync. An AppImage that updates itself looks for its .zsync file on the latest GitHub Release, so the release needs these two; the download server doesn't get them. It never creates or publishes that release and never changes its notes. It doesn't change the files of a release that is already published either: it only checks them, and its job fails when one is missing or different.

The release has the files that the workflows of the tagged commit build. On a Stable branch that was cut before master gained a package, those are fewer than six, and the release is complete without it. Publish Builds never deletes a file from the download server. A file of an earlier release that this one doesn't build therefore stays in latest/, and the S3 latest/ job shows a warning that names it. Delete it by hand, with its .sha256 file, if it shouldn't be offered any more.

The Play Store upload starts a staged rollout on the production track to 20% of users. CI never widens or completes that rollout.

Only the push of the tag uploads to the Play Store and to TestFlight. A platform workflow that someone starts by hand for the tag (Run workflow on GitHub, or gh workflow run) builds and signs the same packages, keeps them as workflow artifacts, and uploads them to neither store. Publish Builds doesn't count such a run either, so it publishes no download from it.

WARNING

latest/ is what the stable download links point at. One job replaces its files one after another, so for the minute or two that this takes it holds a mix of the previous release and the new one. No staging area exists, and latest/ goes back to an earlier release only when someone asks for that by hand (If a job fails midway).

WARNING

Some publishing steps are skipped, without failing the job, when their repository secrets or variables are missing:

  • Download server: without AWS credentials (AWS_ROLE_ARN, or AWS_ACCESS_KEY_ID with AWS_SECRET_ACCESS_KEY) the Publish Builds jobs upload nothing and show a warning. Without AWS_DISTRIBUTION_ID the files are uploaded but the CloudFront cache isn't invalidated, so the download links can serve the previous files until their cached copies expire; the job shows a warning for this too.
  • Android signing: without ANDROID_KEYSTORE_PASSWORD the APK is signed with a throwaway debug key and is still uploaded.
  • Play Store: without GOOGLE_SERVICE_ACCOUNT the upload step is skipped.
  • TestFlight: without all of APPSTORE_API_PRIVATE_KEY, APPSTORE_CERTIFICATES_FILE_BASE64, APPSTORE_CERTIFICATES_PASSWORD (secrets) and APPSTORE_TEAM_ID, APPSTORE_ISSUER_ID, APPSTORE_API_KEY_ID, APPSTORE_PROVISIONING_PROFILE_NAME (variables), the job builds an unsigned IPA and skips the upload.

A green run therefore doesn't prove that a step published anything; check each one as described in Verify. The macOS job is different: upstream it fails when its signing secrets are missing.

3. Verify ​

  1. Workflow runs. List the runs for the tag and wait until all of them have finished:

    sh
    gh run list --repo mavlink/qgroundcontrol --branch vX.Y.Z

    Publish Builds runs aren't in that list, because they run on master:

    sh
    gh run list --repo mavlink/qgroundcontrol --workflow publish.yml --limit 10

    One starts each time Linux, Windows, MacOS, or Android completes, and is named after it, for example Android completed for vX.Y.Z. The run that follows the last of the four publishes. The earlier ones finish at once, and their summary names the workflows they are still waiting for.

  2. Downloads. Each of the six files in latest/ must be the new build. Its Last-Modified time must be later than the tag push, and its checksum must match the copy in builds/vX.Y.Z/:

    bash
    base=https://d176tv9ibo4jno.cloudfront.net
for file in QGroundControl-x86_64.AppImage QGroundControl-aarch64.AppImage \
            QGroundControl-installer-AMD64.exe QGroundControl-installer-ARM64.exe \
            QGroundControl.dmg QGroundControl.apk; do
    curl -sI "$base/latest/$file" | grep -i '^last-modified'
    diff <(curl -s "$base/latest/$file.sha256") <(curl -s "$base/builds/vX.Y.Z/$file.sha256") && echo "$file matches"
done

    A file that wasn't uploaded keeps its old time. The summary of the publishing Publish Builds run lists what its S3 builds/ and S3 latest/ jobs uploaded, and latest/published.json names the tag and the commit that latest/ holds. After a patch release on an older Stable line, latest/ must be unchanged instead: check the files in builds/vX.Y.Z/.

  3. Release files. The draft GitHub Release must hold 14 files: the six packages, their .sha256 checksums, and the two AppImage .zsync files:

    sh
    gh release view vX.Y.Z --repo mavlink/qgroundcontrol --json isDraft,assets --jq '.isDraft, .assets[].name'

    The GitHub Release assets job of the publishing Publish Builds run attached them, and its summary says what it did.

  4. Smoke test. Download each file from latest/, install it, and check that it starts and reports the new version. Open the DMG on a Mac to confirm that Gatekeeper accepts it.

  5. Android signing. In the Android run, the Android (linux) job must have skipped its Create Debug Keystore step. If the step ran, the published APK is signed with a debug key.

  6. Play Store. In the same job, the Deploy to Play Store step either succeeded or was skipped. It's skipped without GOOGLE_SERVICE_ACCOUNT, and in every run that the push of the tag didn't start. After a success the Play Console shows the release on the production track at 20%.

  7. TestFlight. In the iOS run, the iOS (device) job's Upload to TestFlight step either succeeded or was skipped. When it's skipped, the job carries a notice that starts with App Store signing secrets or variables are missing. In a run that someone started by hand it's always skipped, and with the signing secrets set the notice starts with Only the push of the tag uploads to TestFlight. After a success the build is listed under TestFlight in App Store Connect.

  8. Docker Hub. The dronecode/qgroundcontrol tags include <variant>-<short commit> for the tagged commit.

  9. Provenance (optional). gh attestation verify <file> --repo mavlink/qgroundcontrol confirms that a downloaded file was built by this repository's workflows.

4. Manual steps ​

  1. GitHub Release. Open the draft that the Release workflow created for the tag. A Stable branch whose Release workflow predates this (such as Stable_V5.1) gets no draft; run the Release workflow manually from master with the tag instead.
    1. Edit the notes (see Release Notes).
    2. Check the release files. Publish Builds attached the six files, their checksums, and the two .zsync files once all four platforms had passed (Verify). The download buttons in the repository README.md link to the packages by name. If they're missing, see If a job fails midway. A release from Stable_V5.0 or Stable_V5.1 has none: attach its files by hand before you publish it, as described there.
    3. Publish the release. CI never does, and it doesn't change the files of a release once it's published. Publish it only after the GitHub Release assets job has passed. Published earlier, the release keeps the files it has: the job changes nothing, fails, names the files that are missing, and says how to attach them with force_release. A release that GitHub shows as Immutable can't be repaired at all, with force_release or by hand, so for such a release the order is a hard rule. GitHub makes a release immutable when it's published while the repository's release immutability setting is on, which it was for v5.1.0 to v5.1.5 (see Release immutability in .github/ci-notes/platforms.md). Mark a release candidate as a pre-release; otherwise GitHub shows it as the latest release, which is where those download buttons lead.
  2. Version check file. Update latest/QGC.version.txt in the S3 bucket (https://qgroundcontrol.s3.us-west-2.amazonaws.com/latest/QGC.version.txt) to the new version. QGC reads this file at startup and tells users that a new Stable is available, so do it last, after the checks in Verify pass.
  3. CloudFront. CI invalidates the cache of builds/vX.Y.Z/ and of latest/ only when it uploads to them. Files you update by hand afterwards, such as QGC.version.txt, can take up to 24 hours to refresh through CloudFront unless you invalidate their cached copies manually.
  4. Play Store. Widen the rollout from 20% in the Play Console when you are satisfied with the release.
  5. Master. Make sure every fix on the Stable branch is also on master.

5. If a job fails midway ​

When a platform workflow fails, nothing has reached the download server, because Publish Builds publishes only after Linux, Windows, MacOS, and Android have all passed for the tag. Store uploads and builder images of the jobs that ran aren't undone.

  • A failure that isn't caused by the code (a runner, network or service error): use Re-run failed jobs on that workflow run. The job builds the same tag again, and when the workflow passes, its completion starts Publish Builds, which then publishes the release. A re-run belongs to the run that the push of the tag started, so it uploads to the Play Store and to TestFlight as that run does. Don't start the workflow by hand for the tag instead: such a run uploads to no store, and Publish Builds doesn't count it.

  • Publish Builds failed: a failed publish shows up as a failed Publish Builds run, not as a failed build. Its jobs (GitHub daily release for master, S3 builds/, S3 latest/, GitHub Release assets) fail independently, so use Re-run failed jobs on the run within three days; a job whose target already holds the release does nothing. If S3 latest/ failed partway, latest/ holds a mix of two releases until that job passes. If S3 builds/ or S3 latest/ failed in its Invalidate … in CloudFront step, the files are uploaded and correct, and re-running the job sends only the invalidation again. If one of them failed because its record was uploaded but cannot be read back, the files are uploaded, but the download server doesn't let anyone read published.json. Don't ignore that: Publish Builds reads this record to keep an older build from replacing a newer one. Have someone with access to the S3 bucket make the object public again, then re-run the job. If it failed because latest/ has no publication record, nothing was uploaded there and builds/vX.Y.Z/ is complete: have the record written (see Pre-flight) and re-run the failed job. To start a publish by hand, run the workflow from master with the tag as its ref:

    sh
    gh workflow run publish.yml --repo mavlink/qgroundcontrol -f ref=vX.Y.Z

    Add -f dry_run=true to see what it would publish without publishing anything. For a branch, -f commit=<full commit hash> publishes that commit instead of the newest one whose builds have finished, which is how to publish the last good commit when a newer one failed to build a package; a tag needs no commit. A run started by hand publishes the release again even when the download server already holds it, so it's also how to publish a platform that was rebuilt for the same tag by re-running its workflow.

  • A real defect: fix it on the Stable branch and release the next patch version with a new tag. Don't move the existing tag.

  • Going back to an earlier release: latest/ never goes back by itself. Run Publish Builds by hand for the earlier tag with force_latest, which replaces whatever latest/ holds:

    sh
    gh workflow run publish.yml --repo mavlink/qgroundcontrol -f ref=vX.Y.Z -f force_latest=true

    It publishes that tag's files again, to builds/vX.Y.Z/ and to latest/. It takes them from the tag's own build runs, so it needs their artifacts, which GitHub keeps for 30 days, and a tag whose workflows mark their packages for Publish Builds. After 30 days the run fails in Fetch and verify and says that the runs list no package artifact. Don't re-run the tag's build runs to get the artifacts back: they would upload to the stores and push the builder images again. Otherwise someone with access to the S3 bucket has to do it by hand: copy everything in builds/<previous tag>/, including published.json, over latest/ with the public-read ACL, and invalidate /latest/* in CloudFront:

    sh
    aws s3 cp s3://qgroundcontrol/builds/<previous tag>/ s3://qgroundcontrol/latest/ --recursive --acl public-read

    The --acl public-read option is what Publish Builds uploads every file with. A copy doesn't keep the ACL of its source, and the download server serves only objects that have it: without the option nobody can download the copies, and Publish Builds can't read the record. If that directory has no published.json, write the record of the previous tag to latest/published.json instead (Seeding the latest/ record in .github/ci-notes/platforms.md); don't delete it, because the next release then stops for want of a record. Check first that builds/<previous tag>/ still holds all six files.

  • Stores: halt the staged rollout in the Play Console, or expire the build in App Store Connect.

  • Release draft: if the Release workflow failed, run it manually with the tag once the cause is fixed. It doesn't change a release that already exists for the tag. The GitHub Release assets job fails while the tag has no release, because it never creates one: re-run it once the draft exists.

  • Release files: a re-run of GitHub Release assets uploads what the draft lacks and replaces a file whose content differs; other files on the release stay. It changes nothing on a published release, and fails when that lacks a file or holds one with other content. To attach the verified files to a published release, replacing those that differ, start a publish by hand with force_release:

    sh
    gh workflow run publish.yml --repo mavlink/qgroundcontrol -f ref=vX.Y.Z -f force_release=true

    A publish by hand takes the files from the tag's build runs, whose artifacts GitHub keeps for 30 days. After that, attach them by hand: download the files from builds/vX.Y.Z/, with their .sha256 checksums when the directory has them, and add them with gh release upload vX.Y.Z <files> --repo mavlink/qgroundcontrol --clobber, keeping the file names. A tag that was built from Stable_V5.0 or Stable_V5.1 has no checksum files there, because its build jobs upload none. The .zsync files aren't on the download server, so a release that is completed this way has none, and its AppImages can't update themselves from it. None of this works for a release that GitHub shows as Immutable, as it does v5.1.0 to v5.1.5: GitHub accepts no change to its files. The job then fails and says so, with force_release too, and GitHub refuses an upload by hand. Such a release keeps the files it was published with, and the download server still offers its files under builds/vX.Y.Z/.

Don't update QGC.version.txt or publish the GitHub Release until latest/ is consistent again.

Release Notes ​

Three mechanisms exist side by side:

MechanismInputOutput
git-cliff, configured in tools/configs/cliff.tomlConventional Commits subjects since the last tagThe "Changes in vX.Y.Z" section of the draft GitHub Release; just release-notes vX.Y.Z
GitHub's generated release notes, configured in .github/release.ymlRN: labels on merged pull requestsA "What's Changed" list, only when someone presses Generate release notes in the editor
Hand-written textNoneWhat's New, and the release's introduction
  • The Release workflow uses only git-cliff. It lists feat, fix, perf, and revert commits under their own headings and leaves out the other types. Breaking changes of those other types, and commits that don't follow Conventional Commits, go under Other Changes.
  • No workflow uses the RN: labels. They affect a release only if its author presses Generate release notes.
  • What's New describes user-facing changes since the previous Stable and is maintained by hand on each branch.
  • The Play Store listing text comes from deploy/android/whatsnew/, which holds a fixed sentence that points to the GitHub releases.

Recent releases, such as v5.1.5, combine a hand-written introduction, a link to What's New, and a "Changes in vX.Y.Z" list in the git-cliff format.
